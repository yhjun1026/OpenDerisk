## 1. 产品定位:从"对话"到"环境"

市面上 Agent 产品的默认单元是**对话**——每次冷启动,用户反复解释背景、贴数据、纠正口径;对话结束,一切蒸发。场景空间把产品单元从对话升级为**环境**:

> **场景空间 = 一个有准备的工作环境。数据已接好、口径已定义、方法已固化、权限已配好,Agent 进来就能干活,人只在关键节点介入。**

**北极星:沉淀厚度。** 一个新成员(人或 Agent)进入空间,多快能达到"老师傅"的工作水平。空间的所有设计决策都用这把尺子量:这件事做不做、怎么做,看它是否增加空间的沉淀。

由此推出三条基本立场(均已拍板,此处重新组织逻辑链):

1. **交付共享 / 工作过程个人化**——结果属于集体,过程属于个人。
2. **空间是终点,不是入口**——不做跨空间聚合页,用户在空间内完成完整闭环。
3. **空间是资产管理唯一入口**——资产在这里建、在这里维护、在这里被消费,全局 serve 模块只是物理本体。

## 2. 概念模型:空间里到底有什么

### 2.1 内容层:三类内容

```
┌─────────────────────────── 场景空间 ───────────────────────────┐
│  ① 数据资产(名词:能"碰"什么)                                  │
│     DB · Excel/CSV 数据集 · 知识库 · 参考表                      │
│     治理:授权 / 读写范围 / 敏感级 / 新鲜度 / 维护者               │
│                                                                │
│  ② 能力(动词:能"干"什么)                                      │
│     skill · MCP · 内置工具                                       │
│     治理:启用 / 版本 / 来源可信度                                │
│                                                                │
│  ③ 组织层(空间的沉淀:怎么理解 & 怎么干)                         │
│     ECP 语义 = 学习和定义 → "数据是什么、怎么算才对"(声明式)      │
│     剧本     = 关联和使用 → "活怎么干"(过程式)                    │
│     治理:引用完整性 / 漂移失效 / 权限投影                         │
└────────────────────────────────────────────────────────────────┘
```

- **能力消费资产,组织层把两者编织成可复用的工作方式。**
- 组织层是空间独有的 know-how:数据可以重连、MCP 可以重装,但确认过的口径和固化的流程是真正的积累。**组织层 = 沉淀厚度的实体。**

关键边界(防止概念混淆):

| 易混对 | 边界 |
|---|---|
| skill vs 剧本 | skill 是通用方法(跨空间复用);剧本 = 能力 × 具体资产绑定(空间内实例化) |
| MCP 是能力还是资产 | 纯工具型 MCP = 能力;包业务系统的 MCP = 能力通道,背后数据源应登记为数据资产,条目上标注"数据来自 XX"即可,不建额外模型 |
| 知识库 | 数据本体 = 资产;RAG 检索 = 它暴露的能力面 |
| 产出 vs 交付 | 产出 = final_message + deliver_file 标记文件(Agent 产生);交付 = 纯代码后处理(email/飞书/钉钉/in_app,与 Agent 无关) |
| 待办 vs 任务 vs BAIZE TODO | 待办 = "需要我干预"的阻塞事件收件箱;任务 = 一次执行(可能自动跑完不产生待办);BAIZE TODO = 任务内 agent 子步骤,两者不合并 |

### 2.2 运转层:两个闭环 + 一个阀门收件箱

**工作闭环(把活干出来)** — 已落地:

```
剧本(怎么干) × 触发源(何时干) → 任务(一次执行) → 产出 → 交付 → 交付资产沉淀
                    ↑
              待办/干预(人介入解除阻塞)
```

**治理闭环(让数据可信)** — 主体完成,回路未闭合:

```
资产登记 → spec 学习 → ECP 提案 → 人确认 → 语义目录(verified)
    ↑                                        │
    └────── 漂移检测 → 新提案 ←──────────────┘
              │
执行时:ECP 工具(verified 信任标记);execute_sql 命中硬门禁(降级体)
```

**两个闭环的咬合点(设计的精髓):**

1. 剧本引用 ECP 托管资产 → 物化自动得到降级体(schema 只读 + 语义工具)——**治理不是额外负担,是让剧本跑得对的条件**。
2. 任务产出文件可沉淀为数据资产(Excel 升格进 spec 学习链)——空间越用越厚。
3. 两个闭环共用同一个"人的回路":提案确认和执行干预都进收件箱。

**人机分工宪法:**

> Agent 自动跑,跑到需要人的地方,变成一条待办,出现在该出现的人的收件箱里。人不在流水线里,人在流水线的**阀门**上。

阀门的全部来源(定义死,不扩散):Intervention(执行卡住)、ECP 提案(语义确认)、交付审批(外发)、转交(责任转移)、手动待办。

### 2.3 权限:一个公式

> **能不能调(能力门禁) × 能不能碰(资产门禁)**

- Agent 绑能力(capability_pack)→ 决定工具面;绑资产 → 决定数据面。
- 资产注册进 ECP asset_ref = 治理意图声明 → 自动降级(完全体→降级体)。
- 剧本的权限 = 引用集合的投影:执行者需全部引用资产权限,降级规则物化时生效。

**设计纪律(实测换来的):prompt 软约束打不过工具可用性。一切治理落工具面硬门禁,prompt 只做引导。** 此纪律约束未来所有新能力接入。

## 3. 用户模型:一般用户如何在空间内完成所有工作

"完成所有工作"拆解为三种工作模式,全部发生在空间内:

### 3.1 消费(问 / 跑)

用户在右列对话框提问或发起任务。Agent 的上下文由空间注入(资产目录、剧本清单、触发规则、语义目录)——**用户不需要知道数据在哪、口径是什么,空间知道**。

- 临时问题 → 对话直接答(DBCapability/ECP 工具)
- 重复性工作 → 跑剧本(立即执行一次)
- 周期性工作 → 建触发源(订阅,timer/webhook/alert)

### 3.2 干预(收 / 批)

每天进空间第一站是**我的待办**(lobby + rail)。逐条处理:对话驱动(让 agent 做)或手动推进(接手/完成/关闭)。处理完阀门,流水线继续自动跑。

### 3.3 贡献(沉淀)

用户同时也是空间的建设者(公共环境定位):

- 上传 Excel / 接 DB → 自动学 spec → ECP 提案出现在待办 → 确认 → 资产"就绪"
- 把一次成功的临时任务 distill 成剧本 / 沉淀资产
- 作为维护者保证自己名下资产的新鲜度

### 3.4 三类用户时刻

| 时刻 | 用户是谁 | 空间要给他什么 |
|---|---|---|
| **第一小时(新人)** | 刚被拉进空间 | 10 秒内回答:这空间是干嘛的、有什么数据、Agent 会干什么、有哪些现成剧本可跑 |
| **每一天(日常)** | 空间的常规使用者 | 待办驱动:阀门清零 → 收交付 → 临时问题随手问 |
| **每一周(贡献者)** | 维护者/剧本作者 | 资产新鲜度可视、提案确认高效、剧本改动有引用保障 |

**当前产品对"第一小时"支持最弱**——这是差距分析的重点之一(见 §6)。

## 4. 信息架构设计

### 4.1 原则

1. **菜单按用户意图分,不按概念归属分**(剧本是组合资产,但用户找它是想"跑活",跟任务走)。
2. **不拆底层体系**——资源协议、capability 机制不变;IA 是理解层清晰化,不是重构。
3. **所有人工阀门只有一个收件箱**——Intervention、ECP 提案、交付审批、转交都进 inbox,不再有第二个"待处理"页面。
4. **空间内闭环**——用户不为任何日常操作跳到空间外的全局页面(/ecp、全局 datasource、全局 skill 管理)。

### 4.2 目标 IA(顶 nav)

```
场景空间
├── 工作台(lobby,默认)     我的待办 + 空间导览 + 最近交付 + 成长卡
├── 任务                    执行记录(默认"我的")| 触发规则
├── 剧本                    列表 + 编辑器(怎么干)
├── 资产                    数据资产 | 交付沉淀 | 能力   三个 tab
└── 设置                    基本信息 + 成员
```

### 4.3 现状 → 目标映射

| 现状(顶 nav / 页面) | 目标 | 动作 |
|---|---|---|
| Playbooks | 剧本 | 保留 |
| Subscriptions(tasks?tab=) | 任务(执行记录 \| 触发规则) | 保留,默认过滤"我的" |
| Delivery Space(独立页) | 资产 → **交付沉淀** tab | 并入 |
| Interventions(独立页) | 收件箱的来源筛选视图(source_type=intervention) | **降级,撤下顶 nav** |
| Settings | 设置 | 保留 |
| resources 页(裸绑定表) | 资产 → **数据资产** tab | 升级为统一资产面板 |
| assets 页(workspace memory) | 资产 → 交付沉淀 tab 内的"沉淀资产"区 | 并入 |
| datasets 上传(仅后端) | 数据资产 tab 内"上传数据集" | **补 UI** |
| (不存在) | 资产 → **能力** tab | **新增**:skill/MCP 列表 + 启停 + 版本 |
| /ecp(空间外独立页) | 数据资产详情的"语义"视图 + 提案进收件箱 | **折叠进空间** |
| lobby(我的待办/最近产出/成长卡) | 工作台 + **空间导览卡** | 补导览 |
| `/app/scene` 旧页 + `derisk_serve/asset` ES 模块 | — | 标记 legacy,不投入(另行清理) |

### 4.4 资产页三 tab 的职责边界

**数据资产 tab**(能碰什么):
- 列表:DB / 数据集 / 知识库,卡片带**类型、维护者、新鲜度(最近学习时间)、就绪状态(spec/语义覆盖)、归属(引用 vs 本空间自持)**。
- 动作:连接 DB(内嵌表单)、上传 Excel/CSV、挂知识库、重学 spec、删除(带引用检查)。
- 详情 drawer:schema/spec 摘要、ECP 语义目录(该资产的 verified 对象)、血缘(被哪些剧本引用)。

**交付沉淀 tab**(干出来了什么):
- 合并视图:产出物 artifacts + 交付记录 deliveries + 沉淀资产(workspace memory),类型筛选。
- 这是"交付共享"立场的展示面:所有人看到所有交付结果。

**能力 tab**(会干什么):
- skill / MCP 列表:名称、来源、版本、启用状态、"数据来自 XX"标注(业务型 MCP)。
- 动作:启用/禁用、配置。管理动作刻意轻——能力不放维护者/新鲜度(放着不维护顶多是没人用,资产放着不维护会骗人)。

### 4.5 工作台(lobby)补"空间导览卡"

面向"第一小时"用户,lobby 顶部增加导览卡(老用户可折叠):

```
┌──────────────────────────────────────────────┐
│ 这个空间是干什么的:[workspace 简介]            │
│ 📊 数据资产 12(8 已就绪) · 🔧 能力 6 ·        │
│ 📖 剧本 5(3 有定时触发)                        │
│ [随便问问] [跑一个剧本] [订阅提醒]              │
└──────────────────────────────────────────────┘
```

三个动作就是三种消费模式的入口。数据来源全部已有(workspace_resource 计数、readiness、playbook/trigger 计数)。

## 5. 完整用户旅程(目标态)

**新人第一小时**:进入空间 → 导览卡知道有什么 → 对话框问一个数据问题(Agent 带着资产目录和语义口径答)→ 跑一个现成剧本 → 订阅一个触发源。**全程未离开空间,未读任何文档。**

**日常一天**:进空间 → lobby 我的待办(3 条:1 个干预、1 个 ECP 提案、1 个转交任务)→ 逐条处理(对话驱动 / 手动推进)→ 看到昨晚定时任务的交付(交付沉淀 tab / in_app 通知)→ 临时问题对话发起 adhoc 任务 → 下班前任务 close 时 distill 沉淀。

**贡献者一周**:上传新 Excel → 自动学 spec → 待办出现 ECP 提案 → 确认 → 资产就绪 → 写剧本引用它 → 配触发源 → 下周脚本自动跑、自动交付。

## 6. 差距分析:现状 → 目标

| # | 差距 | 现状 | 影响 |
|---|---|---|---|
| G1 | **IA 未收敛** | Interventions/Deliveries 独立页,与 rail 待办功能重叠;resources/assets 两页割裂 | 用户面对三个"待处理"入口和两个"资产"入口,心智分裂 |
| G2 | **数据资产面板未统一** | resources 是裸绑定表;datasets 上传无 UI;无新鲜度/维护者/就绪状态 | "空间是资产管理唯一入口"未兑现,加资产还要去全局模块 |
| G3 | **能力视图不存在** | skill/MCP 只能以 resources 绑定行出现,无"这个空间会什么"的视角 | 新人无法回答"Agent 会干什么" |
| G4 | **ECP 在空间外** | 独立 /ecp 页;提案确认不进收件箱(id 体系:string vs int) | 治理闭环的人的回路断了;提案无人确认则语义层空转 |
| G5 | **剧本健康度无保障** | declaration 按名引用,资产改名/删除即断链;无漂移提醒;删除无级联检查 | 组织层(最有价值的沉淀)会悄悄腐坏 |
| G6 | **新人无导览** | lobby 有成长卡/待办/最近交付,无"空间有什么"的导览 | 第一小时体验缺失,新人只能问老员工 |
| G7 | **遗留死代码** | `/app/scene` 页、`derisk_serve/asset` ES 模块、playbook_tools 死代码、Fire Task 垃圾 trigger | 认知负担,误改风险 |

**不列为差距的(刻意不做)**:跨空间聚合页、统一资源注册中心、能力/资产体系性拆分、@mention/交付转发(P3 视情况)。

## 7. 分期路线图

> 原则:每期结束都有一个**可验证的用户能力**提升;后端已有能力的优先补 UI(G2/G3 大部分是 UI 债)。

### P0:IA 收敛 + 统一资产面板(前端为主)

**目标能力:用户在空间内完成所有资产操作,不跳全局模块;只有一个"待处理"入口。**

- 顶 nav 收敛:Interventions 页降级为收件箱筛选视图,Deliveries 并入资产页
- 资产页三 tab 框架;数据资产 tab = resources 页升级(内嵌创建表单、类型/归属/新鲜度展示)
- datasets 上传 UI 接到数据资产 tab(后端已有:`POST /workspaces/{id}/datasets/upload`)
- 交付沉淀 tab = deliveries + artifacts + 沉淀资产合并视图
- **验证**:tsc 干净;手动走通"空间内上传 Excel → 出现在资产列表";顶 nav 只剩 工作台/任务/剧本/资产/设置

### P1:能力视图 + 空间导览

**目标能力:新人 10 秒知道空间有什么、会什么、怎么干。**

- 能力 tab:从 workspace_resource(type=skill/mcp)+ capability_pack 读,列表 + 启停 + "数据来自"标注
- lobby 空间导览卡(简介 + 三类计数 + 三个动作入口)
- **验证**:新账号进空间,不看代码能说出"有什么数据、Agent 会什么、有哪些剧本"

### P2:收件箱收敛 + ECP 接入(后端关键期)

**目标能力:所有人工阀门汇于一个收件箱;治理闭环的人的回路接通。**

- **id 体系统一(前置,阻塞项;已拍板:映射层方案)**:在 inbox 层做 identity 适配——ECP 的 string workspace_id("default")/ confirmer.user_id 在写入 InboxItem 前经映射层解析为 workspace int id / user int id,**不动 ECP 边界**(守住"ECP 不感知 inbox"的单向依赖)。映射层落一张轻量映射表 + 解析服务,未知标识写 Dead Letter 并告警,不静默丢弃。
- ECP 提案 proposed → confirmer 各写一条 InboxItem(shared);confirm → 按 source_id 批量消除
- 交付审批(create_delivery intervention)已在 inbox 链路,补齐消除事件审计
- 资产页内嵌 ECP 语义视图(资产详情 drawer 展示该资产 verified 对象,替代跳 /ecp)
- **验证**:pytest——提案 proposed/confirmed → 待办出现/全员消除;手动:ECP 全流程不进 /ecp 页完成确认

### P3:剧本健康度 + 资产生命周期

**目标能力:组织层腐坏可见、可防。**

- **剧本引用协议升级:按名 → 按 id(一次性搞定,不留双轨)** — 设计要点见 §7.1
- 资产删除 → 引用检查(剧本 declaration、ECP asset_ref)+ 阻止并列出引用方;资产改名 = 纯展示操作,不再断链
- 覆盖上传 → 失效旧 spec → 重学 → 失败保留旧 spec(资产管理已定,此期落地)
- **验证**:pytest——存量剧本迁移后物化结果不变;改名资产后引用它的剧本正常物化;删除被引用资产被阻止并列出引用方

### 7.1 剧本引用协议升级设计(2026-07-31 拍板:按 id,一次性切换)

**现状**:declaration_dsl 按**名称**引用资产/能力,materializer 物化时按名解析。资产改名即断链;重名即歧义;删除无感知。

**目标协议**:declaration 中的引用项以 **id 为唯一真相**,name 只作展示快照。

| 面 | 设计 |
|---|---|
| DSL | 引用字段从 `name` 改为 `resource_id`(workspace_resource.id);`name` 保留为展示冗余,物化时不参与解析 |
| 写路径 | `create_playbook` / `update_playbook` 服务端把调用方给的名称解析为 id(不存在/歧义即报错),**落库只存 id**;Agent 工具的 list 类工具(list_playbooks/list_assets 等)返回 id+name,prompt 引导引用 id |
| 读路径 | materializer 按 id 直查,不再按名解析;展示层用 id 回查最新 name(改名自动生效) |
| 存量迁移 | 一次性迁移:扫描全部 playbook(含历史版本),name → id 解析重写;能唯一解析的直接迁移,歧义/悬空引用输出清单人工处理。**PlaybookVersion 历史版本也迁移**(否则回滚版本即回到旧协议) |
| 切换纪律 | 迁移与读路径切换同一期上线,不设"按名兜底"过渡期——上线后按名解析代码路径直接删除 |

**为什么不要校验兜底临时方案**:按名+校验是双真相(名可改、校验后仍可断),问题只是从"静默断链"变成"报警断链",协议债还在;按 id 后改名天然安全、歧义天然消除、删除检查有精确锚点,一次到位。

## 10. 一页纸总结

> **场景空间是一个有准备的工作环境。** 内容三层:数据资产(能碰什么)、能力(能干什么)、组织层(ECP 定义数据的意义、剧本定义活怎么干——组织层是真正的沉淀)。运转两个闭环:工作闭环(剧本×触发源→任务→产出→交付)与治理闭环(登记→学习→提案→确认→可信执行→漂移再提案),靠"剧本引用托管资产"和"产出回流为资产"咬合。人机分工一条宪法:Agent 自动跑,人只出现在阀门上——所有阀门汇于一个收件箱。权限一个公式:能不能调 × 能不能碰,治理落工具面硬门禁。
>
> **落地五期**:P0 IA 收敛+资产面板(不跳全局) → P1 能力视图+导览(新人 10 秒上手) → P2 收件箱收敛+ECP 接入(阀门归一,id 走映射层) → P3 剧本健康度(引用按 id 一次性切换,沉淀防腐) → P4 三旅程端到端验收。北极星是沉淀厚度:新成员进来,多快能干活。
